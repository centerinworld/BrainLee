## 1. 인수자가 먼저 알아야 할 결론

문제는 단순히 Claude의 plan 모드를 끄면 해결되는 것이 아니다. 현재 목표 분석, 승인형 코드 생성, 실제 대상 저장소, 운영 배포, 데이터 재검증이 하나의 영속 작업으로 연결돼 있지 않다. 이 연결을 구현하고 한 건의 실제 결함을 끝까지 추적해야 한다.

앞서 확인한 Claude/Codex/Qwen/DeepSeek의 코드 생성·적용 성공은 임시 calc 예제에 대한 실험이다. stock_dashboard 수집기나 운영 데이터를 개선했다는 증거가 아니다. 사용자가 버튼을 누르지 않았다는 이유로 실행 부재를 설명하지 않는다. 요청한 실행 경로를 연결하지 못한 구현의 공백을 먼저 해결한다.

최우선 순서: **허위 성공 제거 → 저장소 지정과 영속 큐 → 목표/승인/워커 연결 → 독립 검증 → 실제 결함 한 건에 적용 → 배포·재수집·전후 계측**.

## 4. 목표 구조와 실제 실행 흐름

```text
주기/수집 완료 이벤트
  → 읽기 전용 진단 → 원천 대조 → 구조화된 결함(finding)
  → 변경 명세(change_request) 및 중복 방지 키 저장
  → 사용자 승인 범위 확인
  → 영속 QUEUED 작업
  → 독립 워커가 lease 획득
  → 지정 저장소 격리 clone + 코드 생성/파일 수정
  → 고정 검증기·회귀 테스트 + 독립 리뷰
  → 정확한 diff와 증거를 READY_FOR_REVIEW로 저장
  → 기존 승인 범위 안이면 진행, 범위 밖이면 필요한 추가 승인만 요청
  → 원 저장소 적용 → 배포 어댑터 → 제한된 재수집/재검사
  → 전후 결과 기록 → VERIFIED 또는 실패/롤백
```

핵심은 알림이 실행을 담당하지 않는다는 것이다. 알림이 실패해도 작업과 승인 상태는 DB에 남아야 한다. 승인을 받으면 실행 워커가 큐를 읽어 진행하며, 사용자가 다시 같은 지시를 할 필요가 없어야 한다.

기존 데몬은 세션 상태 감시 역할로 이름과 화면 설명을 고정한다. 실행 책임은 별도 워커에 둔다. 기존 인계 함수가 필요하다면 새 작업 등록 서비스의 얇은 어댑터로 바꾸고 실제 반환 job_id와 접수 상태만 전달한다. 같은 일을 수행하는 세 개의 큐를 병렬 유지하지 않는다.

## 5. 영속 계약과 상태 전이 — 신규 구현안

아래 필드와 서비스 이름은 **제안이며 현재 API에 존재한다고 가정하지 않는다**.

### 5.1 작업 명세

필수 필드: `job_id`, `goal_id`, `finding_id`, `repo_id`, `base_sha`, `source_fingerprint`, `allowed_paths`, `instruction`, `provider`, `model`, `test_profile_id`, `acceptance_checks`, `approval_scope`, `approval_hash`, `requested_by`, `created_at`, `evidence_manifest_hash`, `retry_budget`, `deadline`.

- repo_id는 서버 측 등록 목록으로 해석한다. 요청자가 임의 절대 경로를 지정하지 못하게 한다.
- 소스 해시는 커밋과 대상 파일 해시를 함께 기록한다. 다른 세션의 미커밋 파일은 덮어쓰지 않는다.
- 승인 해시에 저장소·파일·모델 정책·테스트·배포·DB 수정 범위를 모두 포함한다. 변경 시 기존 승인 범위를 재평가한다.
- 중복 키는 목표+결함 규칙+정규화된 대상 키 집합+원천 버전으로 계산한다. 스캔 시각만 바뀌었다고 동일 결함 작업을 또 만들지 않는다.
- 원천 텍스트/뉴스/모델 산출물은 데이터이며 승인·명령으로 해석하지 않는다.

### 5.2 영속 테이블

`code_jobs` 또는 기존 jobs 확장: spec, status, revision, lease_owner, lease_expires_at, heartbeat_at, attempt, next_retry_at, deadline, last_error_code.
`job_events`: append-only 전이 이력, actor, 이전/다음 상태, 시각, evidence hash.
`approvals`: actor, scope/hash, expiry, consumed_at, revoked_at. 승인 기록과 작업 전이는 한 트랜잭션으로 묶는다.
`notification_outbox`: 알림 내용 참조, 상태, 시도 횟수, 다음 재시도, 외부 message_id. 비밀 토큰은 저장하지 않는다.
`approval_tokens`: 짧은 불투명 토큰의 해시, job_id, action, diff/spec hash, user/chat 제한, 만료, 소비 상태.

### 5.3 상태

기존 `AWAITING_APPROVAL → APPROVED → RUNNING → READY_FOR_REVIEW → APPLIED_TO_WORKSPACE`는 호환성을 유지하며 다음 구간을 명시한다.

| 제안 상태 | 증거 / 다음 행동 |
|---|---|
| QUEUED | 승인된 명세, 실행 예정 시각, 큐 DB 영속 저장 |
| RUNNING | 워커 lease, 시도 ID, 단계별 heartbeat |
| WAITING_PROVIDER | 429/서비스 장애 원인·재시도 시각·횟수 |
| READY_FOR_REVIEW | diff hash, 실제 테스트 수·결과, 독립 검토 증거 |
| APPLYING / APPLIED_TO_WORKSPACE | 적용 전후 파일 hash; 작업 트리 적용만 의미 |
| DEPLOYING / DEPLOYED | 승인된 릴리스 SHA, 서비스 health, 실제 로드 버전 |
| VERIFYING / VERIFIED | 동일 범위의 전후 데이터 검사와 원천 일치 증거 |
| FAILED / TEST_FAILED / APPLY_FAILED | 실패 단계와 원인, 후속 처리 |
| NEEDS_RECONCILIATION | 종료 중단 등으로 적용 여부 불명; 파일/DB 증거 재대조 |
| REJECTED / EXPIRED / ROLLED_BACK | 거부·만료·복구의 실제 기록 |

RUNNING lease 만료 시 무조건 재실행하지 않는다. 생성/테스트는 새 시도로 재개할 수 있지만 적용·배포·DB 변경 중 중단은 먼저 실제 상태를 대조한다. 처리 보장은 “정확히 한 번”이라고 주장하지 않고, 재전달 가능 큐와 멱등성·결과 대조로 중복 효과를 막는다.

## 6. 파일별 구현 순서와 통과 기준

| 순서 | 파일 / 작업 | 통과 기준 |
|---|---|---|
| P0-1 | 기존 데몬 dispatch, approved_code_routes, telegram_approval_poller의 성공 표시 수정 | HTTP 실패·APPLY_FAILED·ROLLBACK_FAILED에서 성공 알림 0건 |
| P0-2 | Telegram 수신기 단일 소유권, 짧은 token 방식, 사용자 식별, outbox | callback ≤64 bytes; 누락 설정·다른 사용자·만료·재전송 입력 거부; 승인 중복 실행 0건 |
| P1-1 | 신규 repo registry, CodeJobs/패치 서비스에 repo context 주입 | 두 임시 저장소 병렬 실행 시 상호 오염 없음; stock 경로 실측 후 등록 |
| P1-2 | 신규 durable worker와 lease/recovery | 승인 직후 웹 종료·워커 강제 종료 후 유실 없이 복구; 적용 중단은 reconciliation |
| P1-3 | strict→finding→code-job 어댑터 | 같은 결함 반복 감지해도 작업 한 개; 실패한 작업 상태가 목표 화면에 그대로 반영 |
| P2-1 | 역할 계약 및 모델 출력 검증 | 역할 위반 결과는 다음 단계로 승격되지 않음; 공급자 실패를 다른 모델 성공으로 위장하지 않음 |
| P2-2 | 독립 검수와 증거 manifest | 변경된 파일/테스트/리뷰/원천 참조가 동일 spec·diff 해시에 묶임 |
| P3-1 | stock 실제 회귀 결함 한 건 구현 | 기존 코드에서 실패, 수정 코드에서 통과; 범위 밖 파일 변경 0건 |
| P3-2 | 배포·재수집 어댑터 및 전후 검사 | 실제 로드 SHA와 검사 범위 일치, 대상 오류 감소 및 정상 데이터 보존 |
| P4 | 재시작·할당량·알림 실패 운영 관찰 | 정의한 관찰 창 동안 큐 유실·허위 성공·무단 범위 확장 0건 |

패치 모듈의 전역 REPO_ROOT를 실행 중 임시 치환하는 방식은 금지한다. 동시 작업이 다른 저장소를 건드릴 수 있다. `RepoContext(root, base_sha, test_profile, runtime)`를 인자로 전달하거나 저장소별 불변 서비스 인스턴스를 만든다. symlink는 resolve 후 등록된 루트 내부인지 검사한다. 격리 디렉터리는 job별 고유 경로로 보존한다.

현재 테스트 모듈은 “이미 커밋된 파일이며 수정 대상 밖”이어야 한다. 실제 결함 회귀 테스트가 아직 없다면 먼저 신뢰된 담당자가 재현 테스트를 별도 변경으로 작성·검토하고 기준 커밋에 포함해야 한다. 이 준비 없이 현재 create API에 새 테스트 이름을 넣으면 실패한다. 모델이 자기 테스트만 고쳐 통과하는 구조로 바꾸지 않는다.

## 7. 승인과 Claude plan 모드 처리

사용자 의도는 승인 후 실제 코드 수정이 실행되는 것이다. 모든 분석·검토 호출의 권한을 올릴 필요는 없다. 생성 단계는 파일 diff를 만드는 실행 능력을 갖고, 독립 검토 단계는 읽기 전용으로 둔다.

현재 공통 generator는 각 모델의 파일 내용 JSON을 받아 신뢰된 컨트롤러가 실제 파일을 수정한다. 이 방식도 결과 파일이 바뀌고 검증을 통과하면 코드 수정 실행이다. 다만 네이티브 Claude/Codex 에이전트가 탐색·도구 호출·테스트를 반복하는 방식과는 다르므로 화면에 구분해서 표시한다.

향후 네이티브 실행 어댑터를 도입하려면 설치된 CLI의 지원 인터페이스를 확인하고 격리 경로·허용 도구·비용·시간·명령 정책을 동일 작업 명세에 묶는다. 승인 실패를 세션 변수 제거, 권한 강제 우회 플래그, 다른 모델로 동일 차단 작업 재시도하여 해결하지 않는다. 안전장치가 거부하면 해당 단계와 이유를 작업 상태로 기록하고 공식 승인 경로를 사용한다. 사용자 승인은 서비스/OS의 실제 권한을 자동으로 바꾸지 않는다.

이전 Claude 차단은 당시 auto mode 실행 분류기 기록으로 확인한 사건이며, 모든 코드 수정 자체가 불가능하다는 뜻은 아니다. 세부 기록은 `/Volumes/Realtek_NVME/AI System/handoff/CLAUDE_APPROVAL_BLOCK_CORRECTION_2026-09-14.md` 참조.

승인 정책 제안:

- 이미 명시적으로 허용된 분석·구현·격리 검증은 다시 승인을 물으며 멈추지 않는다.
- 승인 레코드가 실제 수정·배포 범위까지 포함하면 그 범위 안에서는 추가 버튼 없이 진행한다.
- 현재 시스템의 1차 생성 승인과 2차 diff 승인을 영구 요구사항으로 고정하지 않는다. 승인 범위를 좁게 받았을 때만 추가 승인 지점이 필요하다.
- 포괄적인 “고쳐줘”를 임의의 미래 운영 DB 대량 변경·비용 무제한 실행 승인으로 저장하지 않는다. 운영 효과를 낼 명세를 구체화한다.
- 이번 핸드오프 작성 요청은 기존 작업의 승인 레코드를 대리 생성하라는 요청이 아니다.

## 8. 모델별 역할 계약

이 무결점 목표에는 사용자가 처음 지정한 좁은 역할을 기본으로 유지한다. 이후 “다른 모델도 코드 수정 가능하게”라는 요청은 어댑터 기능 요구로 해석하고, Qwen에게 핵심 판단을 자동 이관하는 근거로 삼지 않는다. 이 해석은 가정으로 기록한다.

| 모델 | 이 목표에서 지시할 일 | 제출 형식 / 제한 |
|---|---|---|
| Gemini | 공식 원천·필드 정의·공개 시각·정정 이력 근거 수집 | URL, 수집 시각, 원문 hash, 관련 필드와 증거. 값을 추측하지 않음 |
| Qwen | 분류, 중복 제거, 필드 추출, 형식 변환 | 스키마 검증 가능한 JSON, 원본 row_id 보존. 오류 심각도·수정 정책·승인 판단 금지 |
| DeepSeek | Qwen 전처리의 누락·중복·단위·키 매핑 점검 | 원본→결과 대조와 mismatch 목록. 점검 실패를 새 추정값으로 덮지 않음 |
| Claude | 독립 검증·반례·보강 | 근거에 접근해 반증 확인, 코드 리뷰. 자신이 구현한 경우 별도 검토 실행을 구분하고 한계를 표시 |
| Codex/구현 담당 | 실행 계약·회귀 테스트·코드 수정·증거 종합 | 기계 검사와 실측 근거에 따라 판정. 모델의 완료 문장만으로 상태 승격 금지 |

각 호출은 요청 모델/응답에서 확인된 모델, 입력/출력 hash, 실제 공급자, 비용·시간, 오류를 기록한다. Gemini 429, DeepSeek 잔액 오류, Qwen 절단 JSON은 미충족 단계다. 모델 이름만 바꿔 동일 단계를 통과시켜서는 안 된다. 코드 생성 어댑터 검증과 이 역할 검수를 별도 시험으로 다룬다.

## 9. 데이터 무결점 목표의 수용 기준과 5단계 증거

“무결점”은 검사 대상·기준 시각·규칙이 명시된 스냅샷의 결과로만 평가한다. 영구적으로 결함이 없다는 보장은 하지 않는다. 미수집 범위를 숨기거나 전부 NULL을 0으로 채우거나 오류 행을 삭제해 건수를 줄이는 방식은 개선으로 인정하지 않는다.

| 데이터 | 필수 검사 |
|---|---|
| 시세 | 거래소/상품/세션별 기대 키, 거래일·상장기간·거래정지 예외, OHLCV 결측·관계, 가격/거래량/금액 단위, 수정주가 여부 |
| 재무 | 법인·접수번호·연결/별도·계정·기간 키, 누적/단일기간, 통화/배율, 정정 공시 버전, 실제 공개시각 |
| 배당/분할 | 이벤트 식별 키, 선언/배당락/기준/지급일 구분, 통화·주당액·분할 비율, 정정/취소 중복 |
| 캘린더 | 예정/실제 상태, 현지 시간대, 변경/취소 이력, 원천 event ID와 공개 시각 |
| 미래참조 | event_time, published_at, ingested_at, available_at, revision 구분. 조회 기준시각보다 뒤에 알려진 값이 과거 판단에 들어가지 않는지 재현 |

미래 일정 자체는 오류가 아니다. 날짜가 오늘보다 크지 않다는 검사만으로 미래참조가 없음을 증명할 수 없다. 결측도 존재하는 행의 NULL뿐 아니라 존재해야 하는 행 자체의 부재를 검사해야 한다. 중복 키는 데이터 유형별로 확정한다.

5단계 증거는 다음 파일 묶음으로 누적한다. 기존 LLM 5회 호출 횟수와 혼동하지 않는다.

| 단계 | 필수 산출물 | 판정 기준 |
|---|---|---|
| 1. 범위·계약 | 대상 테이블/열/키/기간/자산/예외, 운영 DB 정체, 기준시각, source manifest | 검사 누락 영역을 명시하고 기대 행 집합 산출 가능 |
| 2. 외부 근거 | Gemini 원천 자료, 공식 명세, 원문 hash, 채택/기각 기록 | 값·단위·공개 시각을 실제 출처로 추적 가능 |
| 3. 전처리 검수 | Qwen 변환 결과 + DeepSeek 대조 + 결정적 count/key/unit 검사 | 누락·중복·변환 손실 0 또는 정확한 미해결 목록 |
| 4. 독립 검증 | Claude 반례 검토, 재현 실패 테스트, 수정 후 회귀 결과 | 같은 오류를 검출한 테스트가 수정 뒤 통과, 정상 사례 보존 |
| 5. 운영 검증 | 승인/적용/릴리스 hash, 제한 재수집 결과, 같은 범위 전후 지표, 롤백 증거 | 대상 결함 제거 및 회귀 없음. 선행 미충족이면 VERIFIED 불가 |

외부 입력 출발점은 기존 `handoff/goal_1_integrity_20260914/external_sources.json` 및 PLAN_AND_EVIDENCE.md의 공식 PostgreSQL·DART 근거다. 새 데이터 영역별 공식 정의를 추가하고 rule_id·변경 사유·원천을 함께 버전 관리한다. 이번 문서는 새 금융 원천 대조를 수행한 결과가 아니다.

## 10. 첫 실제 데이터 개선 단위

2026-09-14 기준선에는 price_history 10,237,546행, OHLCV 결측 1,385행, OHLC 관계 후보 204,117행, 0값 후보 203,417행, created_at 결측 2,054,113행이 기록돼 있다. 이는 과거 스냅샷이며 현재값이 아니다. 후보 집합은 겹칠 수 있으므로 합산하지 않는다.

**선택 단위:** 결측 후보에서 원천 대조로 확정 가능한 한 종목·한 수집기·한 원인·제한 날짜 범위의 오류를 고친다. 아직 특정 수집기 경로나 종목을 확정할 증거가 없으므로 임의 파일명을 작업에 넣지 않는다.

1. 운영 PostgreSQL 연결 정체와 현재 스키마를 확인한다. 구 SQLite 사본은 운영 기준으로 쓰지 않는다.
2. 과거 anomaly_samples를 현재 키로 재조회해 재현 여부를 확인한다. 원천 미제공·거래정지·정상 0값과 실제 수집 실패를 분리한다.
3. Gemini 근거와 Qwen/DeepSeek 변환 검수로 원본↔DB 차이를 고정한다. 공식 원천 확인이 안 되는 값은 추정 복구하지 않는다.
4. 해당 값의 수집·정규화·upsert 경로를 추적해 한 원인을 확정한다. 원인이 재현되지 않으면 코드 수정을 시작하지 않고 결함 조사 상태로 남긴다.
5. 원천 응답을 비밀정보 제거한 fixture로 저장하고 기존 코드에서 실패하는 회귀 테스트를 만든다. 원천 fixture 사용권/보존 정책도 확인한다.
6. 파일 허용 목록과 테스트 프로필을 포함한 작업을 영속 등록한다. 승인 범위 안에서 격리 실행한다.
7. 독립 검토 후 수정 배포. 같은 원천 fixture로 성공 확인 뒤 제한 재수집을 실행한다.
8. 동일 대상 키에서 수정 전후 값을 대조하고 주변 정상 키·중복·단위·available_at 회귀를 검사한다.

이 단위의 수용 기준: 원인이 설명되고 실패 테스트가 수정 후 통과하며, 확정된 대상 오류가 0, 비대상 값 변경 0, 신규 중복 0, 원천·단위 일치, 복구 가능한 변경 이력 보존. “모든 데이터 무결점” 목표를 이 한 건으로 종결하지 않는다.

## 11. 배포와 데이터 복구를 실제로 수행하는 방법

소스 파일 적용과 서비스 반영을 별도 상태로 기록한다. repo registry에는 사전 검토된 배포 어댑터를 연결하고 모델이 임의 shell 명령을 만들어 실행하지 않게 한다.

실행 전: 실제 서비스 관리 방식(launchd/keepalive 등), 실행 cwd, Python 환경, 포트, 기존 변경, 배포할 SHA, health endpoint를 읽기 전용으로 확인한다. 현재 문서에는 stock의 배포 명령을 확정할 증거가 없으므로 명령을 발명하지 않는다.

배포: 특정 SHA/패키지를 반영하고 해당 서비스만 재시작한다. health 응답만 보지 말고 실제 로드 버전이 승인된 변경인지 확인한다. 기존 프로세스를 포괄적으로 pkill하지 않는다.

재수집: 허용된 종목/날짜/원천으로 제한하고 dry-run 비교 결과를 저장한다. DB 쓰기는 파라미터화된 고정 코드와 트랜잭션으로 수행한다. 기존 row hash를 조건으로 충돌을 검출하고 멱등 upsert를 사용한다. 원본값·변경값·원천 hash·작업 ID를 보존한다.

롤백: 코드와 데이터의 복구를 분리한다. git reverse patch는 DB를 복구하지 않는다. 코드 후속 수정이 있으면 강제 덮어쓰기하지 않고 대조 상태로 보낸다. 데이터 롤백은 해당 작업이 쓴 버전만 되돌리며 이후 정상 수집분을 덮지 않는다. 대량 변경 전 백업과 복원 시험이 필요하다.

검증: 배포 후 한 번의 API 200으로 끝내지 않는다. 최소 한 차례 실제 수집 주기와 재시작 복구 시나리오를 통과해야 한다. 초기 관찰 창은 24시간을 제안하되 주간/분기 데이터는 그 창으로 신규 수집 정상 여부를 증명할 수 없으므로 해당 주기를 따로 명시한다.

## 12. 시험 목록과 실행 증거

신규 시험은 외부 Telegram 전송과 운영 DB 쓰기를 기본 차단하고 mock transport/임시 저장소를 주입한다. 현재 routes에는 알림이 추가돼 있으므로 예전 HTTP 테스트를 무조건 다시 실행하면 실제 알림을 보낼 위험이 있다.

- 통신: goals/submit 401/500/timeout일 때 접수 성공 금지; 202는 접수일 뿐 실행 완료 아님.
- 승인: 올바른 관리자만 승인, 빈 설정 거부, 사용자·채팅 불일치, 만료, 재사용, spec/diff 해시 변경 모두 검증.
- Telegram: 실제 UTF-8 payload ≤64 bytes; 알림 실패 outbox 재시도; 409 상태 노출; 재시작 시 offset/처리 이력 보존.
- 큐: 중복 승인·동시 워커·웹 재시작·lease 만료·프로세스 중단을 주입; 동일 변경이 두 번 적용되지 않음.
- 저장소: 서로 다른 repo 병렬 실행, 경로 탈출·symlink·기준 HEAD 변경·dirty target 차단, 비대상 변경 보존.
- 생성/테스트: JSON 절단·범위 밖 파일·빈 diff·모델 불일치·실제 테스트 0개·모두 skip·timeout·테스트 중 소스 변경은 통과 금지.
- 운영: APPLY_FAILED/ROLLBACK_FAILED를 성공으로 알리지 않음; 로드 SHA와 manifest 일치; 데이터 복구 후 정상 값 보존.

기존 검증 기록: `/Volumes/Realtek_NVME/AI System/handoff/approved_code_execution_20260914/tests.log` 및 각 provider_result.json. 이전 50개 테스트와 모델 예제 결과는 당시 구현 검증이며, 이후 변경된 텔레그램·운영 연결의 회귀 통과를 뜻하지 않는다.

각 실제 run 디렉터리에는 spec.json, approvals.json, source_manifest.json, model_calls.jsonl, patch.diff, tests.json, independent_review.json, deployment.json, before.json, after.json, rollback.json(실행했을 때), events.jsonl, manifest.json을 남긴다. 실패한 단계는 누락 대신 error artifact를 남긴다. 비밀키·세션 토큰·전체 접속 URL은 증거에 넣지 않는다.

## 13. 운영 화면과 정체 감지

화면에는 계획 문서 수나 프로세스 uptime보다 다음 값을 우선 보여준다: 마지막 실제 진단, 마지막 실제 수정, 마지막 운영 검증 시각, 큐 깊이, 가장 오래된 승인 작업 대기 시간, 단계별 실패 원인, 대기 승인 범위, 현재 배포 SHA.

알림은 상태 변화·실패·사용자 조치 필요 때 보낸다. 반복적인 동일 상태 알림으로 진척처럼 보이게 하지 않는다. 알림 전송 성공을 작업 성공으로 표시하지 않는다.

초기 운영값 제안(미확정): 워커 concurrency=1, heartbeat=15초, lease=120초, provider 재시도 최대 3회+지수 backoff, 한 작업 전체 기한 30분. 장기 테스트는 별도 프로필로 늘린다. 토큰/금액 상한은 실제 요금과 사용자 정책을 확인해 설정해야 하며 무제한을 기본값으로 두지 않는다. 모델 불가 상태에서는 독립적인 읽기 검사만 계속하고 필수 모델 게이트를 건너뛰지 않는다.

## 15. 인수자의 첫 실행 과업과 보고 형식

첫 구현 단위는 P0-1/P0-2의 **거짓 성공 제거와 승인 입력 신뢰성 수정**이다. 실제 DB 결함 수정과 구분해 수행한다. 텔레그램 mock·임시 CodeJobs 저장소에서 실패/중복/만료/크기/권한 케이스를 검증하고 파일 diff와 결과를 남긴다. 이 단위가 통과하면 P1 저장소/영속 큐로 이어간다. 이미 승인된 구현을 계획으로만 반환하지 않는다.

보고는 “수정 파일 / 재현한 문제 / 실행한 검사 / 통과·실패 / 실제 운영 적용 여부 / 남은 연결”을 포함한다. fixture 테스트, 운영 소스 적용, 배포, 데이터 개선, 전체 목표 달성을 각각 구분한다. 다음 담당자는 이 문서를 읽었다는 이유로 과거 실패 단계를 통과 처리하거나 목표를 완료로 바꾸지 않는다.
