# goal_1 반복 산문 경로 교체 — 소스 변경, 운영 미반영

P1-3 목표→code-job 자동 연결은 사용자 방침에 따라 보류한다. code-job은 웹에서 직접 만드는 경로를 유지한다. Claude의 P0/P1 완료 보고와 이번 변경을 구분한다. 기존 완료 보고의 119개 시험을 이번 턴에서 재실행한 것은 아니다.

## 확인한 반복 원인

strict_agi_orchestrator.maintain_goals는 검증 완료 이외 결과에 대해 다음 감시 주기에 다시 LLM 과업을 생성한다. 스캐너 집계는 숫자로 존재하지만 기존 경로는 이를 산문 프롬프트로 변환한다. 따라서 과거 156회 산문을 다시 읽거나 JSON 형식을 모델에 요구하는 것으로 해결하지 않는다. 이 턴에서는 156개 원문을 전부 재검토하지 않았다.

## 이번 소스 변경

- services/integrity_findings.py: PostgreSQL 스캐너 집계에서 결정적으로 후보를 생성한다. DB 정체, 테이블, 규칙, 관측 건수, 증거 해시, 누락 증거를 기록한다. 산문·잘못된 건수·중복 테이블을 거부한다.
- 후보 ID는 DB 정체+테이블+규칙의 집계 그룹 ID다. 개별 오류 행 ID가 아니며 같은 건수가 다른 행을 뜻할 수 있다. 자동 작업 중복 키로 재사용하지 않는다. 관측 시각을 포함한 원본 스캔 해시는 별도 보존한다.
- strict_agi_orchestrator.py: goal_1 신규 자동 실행은 LLM dispatch 대신 스캔과 JSON artifact 저장으로 전환한다. 다음 검사 시각은 기존 cadence_hours(기본 24시간)를 사용한다. 실패도 SCAN_FAILED로 남기고 LLM 오류 분석 루프를 만들지 않는다.
- 항상 code_job_eligible=false. 양수 집계는 NEEDS_REPRODUCTION 후보일 뿐 확정된 수집기 결함이 아니다. 0건도 전체 목표 통과로 판정하지 않는다.
- 자동 연결, 코드 작업 생성, Telegram 전송, 사용자 승인 대리 입력은 추가하지 않았다.

## 검증

backend에서 `../../../antigravity_workspace/venv/bin/python3 -m unittest test_integrity_findings test_strict_agi_orchestrator -q` 실행: **37 tests OK**.

임시 상태 파일과 가짜 스캐너 사용. 운영 singleton/모델/운영 DB를 호출하지 않았다. 후보 ID 안정성, DB 구분, 잘못된 입력 거부, 제한 범위 0건의 전체 성공 오인 방지, goal_1 dispatch 0회, 검사 주기 내 중복 스캔 방지, 스캔 실패 시 민감한 예외 문자열 미노출을 검사했다.

## 운영 제한과 다음 과업

이번 소스는 재배포하지 않았다. 현재 실행 중인 프로세스의 호출량이 줄었다고 주장하지 않는다. 기존 QUEUED/WAITING/RUNNING 과업도 취소하지 않았으므로 그 작업은 기존 경로로 계속될 수 있다. 배포 담당자는 기존 goal_1 작업의 실행 상태를 보존하고, 명시적인 중단/보존 정책으로 처리한 뒤 새 소스를 반영해야 한다. 다른 목표의 반복 정책은 이번 변경 범위 밖이다.

이 구현은 산문 생성 낭비를 차단하는 진단 경로다. 후보의 원인 추적과 개선을 수행하는 워커까지 구현된 것은 아니다. 웹에 후보 전용 UI도 아직 없다. 상태는 goal 응답의 integrity_status/integrity_artifact/integrity_next_scan_at에 기록된다.

다음 데이터 과업은 후보 한 규칙의 실제 행 키와 원천 응답을 읽기 전용으로 확보하고 수집기 경로·재현 테스트·확정 원인을 연결하는 것이다. 이 증거가 준비되면 웹에서 해당 code-job을 직접 생성할 수 있다. P1-3 재개는 이 증거의 실제 품질을 검증한 이후 판단한다. 집계 후보 JSON이 생성됐다는 이유만으로 자동 연결 보류를 해제하지 않는다.
