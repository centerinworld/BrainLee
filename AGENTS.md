# Runtime Stock Dashboard — Agent Rules

## Authoritative live boundary
- Work only in this `runtime/` Git root. The serving API is `uvicorn main:app` on 127.0.0.1:8000; verify its PID, CWD, and active datastore before making operational claims.
- PostgreSQL is the primary store. Use `connect_primary_db()` or `connect_stock_db()` in live paths; do not use direct `sqlite3.connect()` for primary data.
- Price/financial repair scripts default to read-only. A live `--apply` requires an explicit approval, an idempotency rule, backup/audit rows, and independent post-write read-back.

## Numeric data rules (MANDATORY — 2026-10-03, shared by Claude/Codex/Hermes)
- **⛔ PRINCIPLE 0 — NEVER trust DART-parsed values 100%.** A DART value is only a source candidate; it is confirmed only when it matches FnGuide (required) and Naver (secondary), compared separately for consolidated (CFS) and separate (OFS). On any mismatch, suspect OUR parsing first (account id/name, CFS/OFS, 3-month vs YTD, unit/currency, period alignment, restatement). Repeated per-stock differences = parsing problem → record in `stock_collection_config` (`fs_quirk:*`). Target accuracy 99.99%.
- Before judging or modifying prices, financial statements, cash flow, depreciation, order backlog, segment revenue or US financials, read `docs/FINANCIAL_STATEMENTS.md` (Korean) — the single canonical document for ALL numeric data (financial statements, prices, cash flow, order backlog, inventory, depreciation, CapEx, segments, valuation, US financials). It fixes the source of truth per dataset, definitions, tolerance, the mandatory procedure, 23 real failure cases, current accuracy, open items and limitations.
- Record numeric-data work results in §7 of that file (1–3 lines), not in hermes.md or CLAUDE.md.
- **Open items (all docs, incl. user decisions pending): `docs/OPEN_ITEMS.md`.**
- **Start here for current state**: `docs/FINANCIAL_STATEMENTS.md` §9-2-7 (handoff: jobs in progress, remaining work, what not to do) and §7 (chronological log).
- Trading signals (portfolio trend/sell signals, chart-signal verdict, buy-candidate entry) follow `docs/SIGNAL_RULES.md` (Korean, canonical); the only implementation is `trend_rules.py`. Do not add per-screen signal rules.
- Do not change the basis (e.g. FnGuide vs DART, parent vs total) without explicit user approval recorded in that document's change log. Sessions switching bases overwrote the same cells up to 6+ times.
- "Verified/complete" claims require value comparison against the source of truth, with the compared row count. Reclassifying flags, relaxing thresholds or checking row existence is not verification.
- Doc-body (business-report `4. 재무제표` table) OFS candidates are applied only through `scripts/review/apply_ofs_doc_candidates_20261010.py` (contract `docs/EXECUTION_CONTRACT_OFS_DOC_CANDIDATES_20261010.md`): dry-run by default, fresh-runtime FnGuide re-check per cell, NULL-only fills, scale-mismatch rows (`065150`) refused forever. `--apply` requires separate approval; tests `tests/test_apply_ofs_doc_candidates_20261010.py`. New annual rows must be written as **ONE merged row per (table, stock_code, year) group** — never one row per field (that creates duplicate annual keys) — with every merged cell read back and a duplicate-annual-row guard (`duplicate_annual_rows > 0` ⇒ `pass=False`). The canonical sync covers INSERTED rows as well as updated ones (canonical is the only path `signal_data_gate` reads) and keeps an existing canonical value where the ledger row is NULL.

## AGI execution continuity (2026-10-11)
- **A `review`/`blocked` handoff is not a stop.** Whoever returns a verdict must name, in the same turn, the next independent harmless task with its owner, expected artifact, blocker and re-verification command; `@code-doer` starts it immediately. A blocked item never halts the rest of the backlog, and an omitted handoff is an operational defect, not "work finished".
- Recorded defect that created this rule: the OFS `BLOCKED` hold was over-read as a full AGI stop, no next owner/artifact was dispatched, and no durable schedule existed to detect the gap, so an off-peak window was lost (2026-10-11 09:29 KST). Independent continuity check is now a durable schedule (`stock-dashboard-deepseek-offpeak-dispatch`, weekdays 19:15 KST, `deliver=all`); until such a check exists, interrupted work is reported as an operational defect rather than as done.
- DeepSeek API peak (2× price) = **KST 10:00–13:00 and 15:00–19:00 on weekdays** (= 01:00–04:00 / 06:00–10:00 UTC, Mon–Fri, excluding Chinese public holidays); every other hour plus full weekends and holidays is off-peak. Source: `api-docs.deepseek.com/quick_start/pricing` ("Peak hours are 01:00 - 04:00 and 06:00 - 10:00 UTC, Monday through Friday… All other hours are off-peak"). V4 peak/off-peak billing replaced the retired V3/R1 off-peak discount, so the earlier "KST 09:30–next-day 01:30 peak" entry was that retired window and is corrected here. DeepSeek-dependent work runs off-peak; the 19:15 KST dispatch fires just after the peak ends.
- Continuity changes **who is asked to do what next**, never what is allowed: live DB writes, collection, service restarts, external sending and orders keep their existing approval rules.

## Price-integrity safety
- `price_history` has no `quality_status` column. Suspension status is derived by `price_integrity.rebuild_views()` from `volume=0 AND open=high=low=0`; the canonical read view `canonical_price_history_v` (and `canonical_price_returns_v`, which adds `safe_daily_return`) carries the derived `return_usable` flag — `price_history_quality_v` only carries `quality_status`. Rows classified `suspended` have `return_usable=0`.
- Corporate-action/basis evidence must be point-in-time and fail closed. Never infer a price adjustment from a large price jump alone.
- Historical price-limit checks must use the date-sensitive policy in `price_integrity.price_band(day)`: ±15% before 2015-06-15 and ±30% on/after it. For a comparison to the next candle, use that next candle's effective-date band in the inverse direction.
