# Claude → Codex 핸드오프: 재고자산/수주잔고/원재료매입비/특허R&D/공시 검증 결과 (2026-06-16)

## 배경
2026-06-15~16 세션에서 텐버거 프로젝트 페이지의 미수집 데이터(특허/R&D공시, 프로그램매매)를 보완하고,
기존 수집 데이터(재고자산/수주잔고/원재료매입비) 전수에 대해 무결점 검증을 수행했다.
검증 중 다수의 **실질적 데이터 결함**을 발견하여 1차 정리했으나, 구조적 원인 분석과 완전한 재수집은
DART API 일일 한도 제약으로 완료하지 못했다. Codex가 이어서 점검/수정해야 할 사항을 정리한다.

## 1. 재고자산 (`dart_cost_quarterly.inventory_assets_krw`)

### 발견한 버그 (1차 수정 완료)
1. **소액 오염값(2,650건)**: Q4(연말) 행 다수가 "10원"~"수백원" 등 비현실적 소액으로 저장됨.
   - 예: 파두(440110) 2025년 — 실제 411억원인데 DB엔 7원.
   - 원인: `scripts/collect_inventory_from_dart.py`의 스킵조건이 `inventory_assets_krw>0`만 체크해서,
     한 번 잘못된 값이 들어가면 영구히 "수집완료"로 고착됨.
   - 조치: 스킵조건을 `>=1000000`(최소 100만원)으로 강화, 2,650건 NULL 처리 후 재수집.
   - 재수집 결과: saved=1,916 / skip=30,013 / failed=7,011 (38,940건 시도). **잔존 소액오염 0건 확인.**
2. **극단값(3건)**: `inventory_assets_krw`가 1e14(100조원) 초과.
   - 예: 011000(진원생명과학) 2021Q4 = 2.42×10^47원(완전 깨진 값), 323350/032680도 1e15~1e16원대.
   - 조치: 3건 모두 NULL 처리. 수집기에 상한선(`0 < v <= 1e14`) 추가해 재발 방지(`_fetch_inventory` 내부).

### Codex가 추가로 봐야 할 사항
1. **Q4 vs Q1-Q3 10배+ 급변 158건** (`fiscal_quarter=4`의 `inventory_assets_krw`가 같은 연도 Q1-Q3 평균 대비
   10배 이상 크거나 작은 케이스). 연도별로 21~48건씩 분산되어 있어 특정 연도 집중 버그는 아님(2021:22, 2022:22,
   2023:48, 2024:36, 2025:30). 일부는 계절성(연말 재고 변동)일 수 있으나, 표본(NAVER, 한섬, 신세계인터내셔날 등
   대기업 포함)을 보면 Q4 값이 Q1-Q3 대비 1/100 수준으로 작아지는 패턴이 많아 **분기보고서(Q1-Q3, report_code
   11013/11014)와 사업보고서(Q4, report_code 11011) 간 계정 매핑이 다른 계정을 잘못 잡는 구조적 버그**일 가능성이

## 2. 수주잔고 (`order_backlog`, `dart_backlog_quarterly`)

### 발견한 버그 (1차 수정 완료)
1. **음수값**: `order_backlog` 163건, `dart_backlog_quarterly` 4건. 수주잔고는 음수일 수 없음 → 전부 삭제.
2. **2022년 집중 단위오류 70건** (`order_backlog`): 시가총액의 50배를 초과하는 비현실적 거대값.
   - 예: 후성(093370) 2022 — 시총 13,847억원인데 수주잔고 740,417억원(시총의 53배).
   - 비율이 대략 1000배 단위로 나타나는 경우가 많아 **"천원"→"원" 변환에서 추가로 ×1000이 더 곱해지는
     단위 변환 버그**일 가능성이 높다. 2022년에만 69건이 몰려있어(2025년 1건 제외) **2022년 보고서 포맷
     또는 그 해 파서 버전(`backlog_v2` 이전?)에 국한된 문제로 추정**.
   - 조치: 70건(order_backlog) + 1건(dart_backlog_quarterly) 전부 삭제. **단위 변환 로직 자체는 수정하지
     않았으므로 재수집 시 동일 오류가 재발할 가능성이 있음** — Codex가 `dart_backlog_collector.py`의
     2022년 보고서 처리 경로(특히 `_extract_backlog()` 단위 감지 로직)를 직접 재현/수정해야 함.

### 진행 중 이슈
- **수주잔고 재수집이 DART 일일 한도(`status=020`) 도달로 미완료**. 마지막 실행은
  `{'ok': 0, 'no_metric': 29546, 'errors': 0}` — 한도 소진 후 전부 no_metric으로 빠짐(빈 응답을 "수주잔고 없음"으로
  잘못 해석하지 않는지 확인 필요. `_fetch_document_full()`이 020 응답을 명확히 구분해 로깅하는지 점검).
- 수주잔고 수집기(`collectors/dart_backlog_collector.py`)의 `conn.commit()` 주기를 100건→20건으로 단축함
  (긴 미커밋 트랜잭션이 다른 프로세스의 DB 쓰기를 수십 분간 막은 사고 — 아래 "운영 이슈" 참조). 이 변경이
  수집 속도에 미치는 영향은 미미하나, 향후 Codex가 이 파일을 수정할 때 커밋 주기를 다시 늘리지 않도록 주의.

### Codex가 추가로 봐야 할 사항
1. 2022년 단위오류의 근본 원인 파악 (재현: 후성 093370, 한국단자 025540, 오이솔루션 138080 등 2022년 데이터로
   `_extract_backlog()` 직접 호출해 원문 대비 디버깅).
2. 현재 커버리지 33.0%(888/2,693)가 한도(quota) 부족 때문인지, 구조적으로 수주잔고 미존재 업종이 많아서인지
   분리해서 봐야 함. 업종상 가능 후보군(산업재/소재/IT/에너지/경기소비재) 1,691개 중 888개만 확보된 상태.

## 3. 원재료매입비 (`dart_material_purchase`)

### 발견한 버그 (1차 수정 완료)
1. **한진칼 패턴(재발 확인)**: 한진칼(180640)에서 동일하게 비현실적 거대값(35,248,680억원~40,585,098억원)이
   재수집할 때마다 **계속 반복 재발생**함. `extract_material_purchase()`가 10,000자 섹션 윈도우 내에서
   "총계"/"합계" 패턴을 정규식으로 찾는데, 원재료 매입과 무관한 다른 표(예: 지분 구조, 주식 총계 등)를
   오매칭하는 것으로 추정. **파서 로직 자체는 아직 수정하지 않았음** — 임시조치로 저장 상한(`1e9 <= val <= 5e13`)
   만 추가해서 막아둔 상태. 한진칼처럼 매번 같은 잘못된 패턴을 잡는 종목은 재수집할 때마다 같은 오류가
   재발하므로, **`extract_material_purchase()`의 섹션 매칭 정밀도를 근본적으로 개선해야 함**
   (예: "총계"/"합계" 매칭 시 같은 줄에 단위(원/천원/백만원) 문자열이 함께 있는지, 직전 컬럼 헤더가
   품목명/매입액인지 확인하는 등 컨텍스트 검증 강화 필요).
2. **시총 20배 초과 19건**: 성도이엔지(037350, 시총1,652억→매입비33.9조원), 아남전자(008700, 시총996억→
   매입비37.2조원), 컨텍(451760), 코데즈컴바인(047770), 리튬포어스(073570), 아가방컴퍼니(013990, 3개연도),
   희림(037440, 3개연도), 우리엔터프라이즈(037400, 3개연도) 등. 한진칼과 동일한 패턴(섹션 오매칭)으로 추정.
   - 조치: 19건 삭제 + 수집기에 "시총의 20배 초과 시 저장 거부" 룰 추가(`market_cap` 컬럼 활용).

### Codex가 추가로 봐야 할 사항
1. `extract_material_purchase()` 정규식 패턴 5종(`총\s*계`, `합\s*계` 등)이 매칭한 실제 원문 컨텍스트를
   재확인 — 특히 한진칼/아남전자/희림처럼 반복 재발하는 종목들의 원문을 직접 떠서 어떤 표를 잘못 잡는지 디버깅.
2. 현재 커버리지 39.8%(1,072/2,693)는 **DART 일일 한도 초과로 수집이 중단**된 상태(이번 세션 마지막 배치
   `ok=3, err=2199`). 한도 회복 후 재수집 필요. 대상 종목 선정 로직(`get_targets()`)은 소재/산업재/필수소비재/
   경기소비재/IT/에너지 업종 + 시총 500~100,000억 조건만 사용 중이므로, 이 범위 밖 종목은 의도적으로 제외됨
   (전체 미보유 1,621개 중 상당수는 업종 불일치로 정상 제외 추정 — 별도 검증 안 함).

## 5. DART 공시 캐치업 (`dart_disclosures`)

**미완료** — DART API 일일 한도(`status=020`) 도달로 중단됨.
- 최종 실행 결과: 수집=277, 스킵=1,164, 오류=2,444 (오류 대부분 "한도초과" 또는 "database is locked").
- `dart_disclosures.rcept_dt` 최신값이 여전히 `2026.05.08`로, 약 한 달간 정체된 상태가 완전히 해소되지 않음.
- **재발방지 필요**: 스케줄러의 `공시확인` 잡이 매일 자동 실행되는데, DART API 한도초과로 매일 실패하고 있었음에도
  로그가 WARNING 레벨로만 남고 사용자에게 노출되지 않아 한 달간 방치되었다. Codex가 이 잡의 실패를 더 눈에 띄게
  알리는 방법(예: 연속 N일 실패 시 텔레그램 알림)을 검토할 것.
- 수동 재실행 필요: `python3 collect_dart_disclosures.py --skip-days 7 --years 1 --max-calls 3000` (DART 키
  3개 일일 한도 회복 후).

## 운영 이슈 (재발방지 — 모든 DART 배치 수집기 공통)

1. **장시간 미커밋 트랜잭션이 전체 DB를 막는 사고 발생**: `dart_backlog_collector.py`가 100건마다만 커밋하는
   구조였는데, DART 문서 fetch 중 SSL 재시도/네트워크 지연이 겹치면서 한 트랜잭션이 수십 분간 열려있어
   다른 모든 프로세스(재고자산/원재료매입비 수집기, 그리고 본 핸드오프 작성을 위한 단순 UPDATE/DELETE 쿼리)가
   `database is locked`로 실패했다. **SIGSTOP으로 일시정지해도 트랜잭션이 닫히지 않아 효과 없었고, 강제종료
   (`kill -9`)로만 락이 풀렸다.**
   - 조치: `dart_backlog_collector.py` 커밋 주기를 100→20건으로 단축.
   - **Codex가 신규/기존 배치 수집기를 작성/수정할 때 반드시 커밋 주기를 짧게(20건 이하) 유지할 것.**
   - 만약 "database is locked"가 길게(수 분 이상) 지속되면 SIGSTOP이 아니라 프로세스 종료(`kill -9` 후
     재시작)로 해결해야 함을 CLAUDE.md에 기록함.

2. **DART API 3키 공유로 인한 동시 수집 시 한도 조기 소진**: 이번 세션에 재고자산/원재료매입비/수주잔고/

   - 장기 실행 프로세스는 확인되지 않음.
   - DART 한도 회복 후 `collect_dart_disclosures.py --skip-days 7 --years 1 --max-calls 3000` 재실행 및 최신 `rcept_dt` 확인 필요.

4. **미국주식 가격 갱신**
   - API 화면 기준일 불일치는 수정했으나, 백엔드 로그에는 Yahoo Finance 일일 쿼터 소진으로 해외 가격 갱신 0건 이력이 있음.
   - 현재 DB 보유 최신일 분포: 전체 2,099개 중 `2026-06-16` 1종목, `2026-05-29` 599종목, `2026-05-22` 1,489종목.
   - 즉, 화면은 정상 렌더링되지만 미국주식 가격 최신성은 아직 낮음. 쿼터 회복 후 전체 가격 배치 재실행 또는 Yahoo 외 대체 가격 소스 도입 필요.

### D. Claude 재검증 요청 포인트

- `main.py`의 미국주식 목록/상세 가격 소스 우선순위가 의도대로 `us_price_history > us_frontend_snapshot > radar_market_cache`인지 확인.
- 미국주식 `us_price_history` 최신성 문제: Yahoo Finance 쿼터 소진 시 2,000여 종목 갱신이 중단되는 구조를 보완할 수 있는지 확인.
- `scripts/collect_inventory_from_dart.py`의 100만원 미만 차단 기준이 실제 재고자산 데이터에서 정상 소액 기업을 과도하게 누락시키지 않는지 샘플 검증.
- 수주잔고/원재료매입비 장기 실행 프로세스가 실제 진행 중인지, 한도 소진 상태에서 no_metric/err로 잘못 누적하지 않는지 확인.
- 원재료매입비 파서에 “원문 컨텍스트 저장 + 합계 행 헤더 검증”을 추가할지 검토.
