| 섹션 | 내용 |

## 2. 우리 보고서 구성 — 기존 파이프라인에 그대로 매핑

**새로 만들 것은 생각보다 적다.** 아래 섹션은 전부 이미 운영 중인 테이블·API로 채울 수 있다.
AGI-06이 새로 만들어야 하는 것은 "모아서 서사로 엮고, 변경이 생기면 다시 엮는" 조립·갱신
계층뿐이다.

| 리포트 섹션 | 우리 소스(이미 존재) |
|---|---|
| 헤더 카드 | `stock_universe`(발행주식수·외국인비중) + `valuation_history`(PER/PBR·시총) + `analyst_pdf_extracts`(목표가·의견, `/api/reports`가 PDF→추출 중) |
| 분기 Review | `financial_data`/`cash_flow_data`(분기·연간) + `segment_revenue`(법인/부문별) |
| 사업 포트폴리오 | `company_product_mix`(제품별 매출 비중, 연 1회 갱신) — 이번에 OSAT 비교군을 이 테이블 근거로 만든 것과 같은 방식 |
| 공시·이벤트 | `dart_disclosures`(817K행, 거의 실시간) — 유상증자·CB·특허·계약 등 |
| 컨센서스·추정 변경 | `analyst_pdf_extracts`(fwd_eps/fwd_rev/target_price) — 리포트가 새로 들어올 때마다 "기존 추정치→신규 추정치" 비교가 자동으로 생긴다 |
| 뉴스·관심도(좋은/나쁜 뉴스) | **AGI-02(텔레그램)·AGI-03(블로그)** — 지금 막 만든 선택 수집(`ingest_specific_messages`/`ingest_known_posts`)으로 이 회사가 언급된 글만 모을 수 있다. 다만 본문 보관 수준(D07)이 아직 열려 있어 본문 기반 긍/부정 판정은 D07 결정 후에 가능 |
| 비교군(피어 비교) | **이번에 만든 `sector_taxonomy` peer_group**(`stock_sector_membership_v2`, OSAT 7종목) — "같은 비교군 안에서 이 회사는 어디쯔음인가"를 바로 계산 가능 |
| 차트(실적 vs 컨센서스) | 기존 `dataviz` 패턴 재사용 |

## 3. 갱신 트리거 — "다음 분기 실적 나오면, 뉴스 보면 업데이트"의 구체화

보고서는 **고정 문서가 아니라 트리거에 반응하는 것**으로 설계한다. 트리거마다 "무엇이
바뀌는지"와 "어느 섹션만 다시 쓰는지"를 분리해, 매번 전체를 다시 생성하지 않는다.

| 트리거 | 감지 방법(이미 있음) | 바뀌는 섹션 |
|---|---|---|
| 실적 발표(분기/연간) | `financial_data`/`cash_flow_data`에 그 회사의 새 `(year, quarter)` 행 적재 | 분기 Review, 실적 테이블, 밸류에이션 |
| 신규 공시 | `dart_disclosures`에 새 `rcept_no` | 이벤트 섹션(유상증자/계약/특허 등 유형별 분류 필요 — `dart_rd_patent_signals`·`dilution_events` 이미 유형 분류돼 있음) |
| 애널리스트 추정 변경 | `analyst_pdf_extracts`에 새 `report_id` 또는 기존 종목의 `fwd_eps_1y`/`target_price` 변경 | 컨센서스·추정 변경 섹션 |
| 뉴스/관심도 | AGI-02/03 선택 수집으로 그 회사 언급 글 추가(사람이 지정한 글만, D07 전까지는 메타데이터만) | 뉴스 섹션(감성 판정은 D07 이후) |
| 사업 포트폴리오 변화 | `company_product_mix` 연 갱신분이 전년과 비중 차이 > 임계치 | 사업 포트폴리오 섹션 |
| 비교군 재구성 | `sector_taxonomy` 스냅샷이 바뀜(멤버 추가/제거, 신뢰도 변경) | 비교 섹션 |

## 4. 버전 관리 — AGI-01의 revision 개념을 보고서 자체에도 쓴다

리포트도 "이전엔 뭐라고 썼는지"가 남아야 한다(사용자가 반복 지적한 "계속 발전해 나가야
한다"는 과거를 지우는 게 아니라 쌓는 것이다). AGI-01이 이미 만든 `revision_hash`·`change_kind`
·`collected_at` 패턴을 재사용해, 보고서를 **문서 하나가 아니라 회사별 revision 열**로
저장하는 쪽을 제안한다 — 섹션 단위로 쪼개 트리거가 있었던 섹션만 새 revision을 만들고,
나머지 섹션은 이전 revision을 그대로 참조한다(위 §3의 "어느 섹션만 다시 쓰는지"와 연결).

## 6. 질문 1·2에 대한 답 — 관리 화면
