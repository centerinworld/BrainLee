## 2. Codex 보고서에 없던 리스크: `collect_krx_history.py._save_stocks()`가 새 BEFORE 트리거를 통과하지 못함

### 근거
- `_save_stocks()`(collect_krx_history.py:75)는 `gate_price_batch()`를 호출하지 않고
  `INSERT OR IGNORE` 후 실패 시 `UPDATE ... WHERE volume IS NULL OR volume=0`으로 직접 쓴다.
  이 UPDATE는 `open,high,low,close,volume`을 바꾸므로 새 `price_history_basis_write_guard`
  (BEFORE, 미검증 시 `RAISE EXCEPTION`) 대상이다.
- 반면 `collect_kis_ohlcv.py`(:218-224)는 이미 `gate_price_batch()`를 호출해 통과 후
  `app.price_basis_checked=1`을 세션에 세팅한다 — 안전.
- 오늘 밤 다른 세션(`claude/wonderful-swirles-156532`)이 `_save_stocks()`를 이용해 결측
  거래일 1,739개를 재수집(`backfill_gap_dates.py`, 스크린샷은
  `/Volumes/Realtek_NVME/stock_dashboard/.claude/worktrees/wonderful-swirles-156532`
  워크트리 참조)했고, **159,054건의 과거일자 UPDATE가 트리거 강화 전에 성공적으로 커밋**됐다.
  같은 스크립트를 지금(트리거 강화 후) 재실행하면 첫 UPDATE에서 `P0001` 예외로 즉시 크래시한다
  (`_save_stocks` 호출부에 try/except가 없음).

### 스케줄러 작업은 위험하지 않음을 확인
- `_job_krx_daily`(scheduler.py:1339): `bas_dd = today.strftime(...)`만 사용 — 항상 오늘 날짜만
  쓰므로 트리거의 `CURRENT_DATE` 예외에 걸려 안전.
- `_job_supply_daily`(scheduler.py:1589): `inst_net_buy` 등 수급 컬럼만 UPDATE, OHLCV 컬럼은
  건드리지 않음 — 트리거가 `UPDATE OF open,high,low,close,volume`에만 걸리므로 안전.
- 위험은 **`_save_stocks()`를 과거일자 백필/재수집 목적으로 쓰는 임시 스크립트**에 한정된다
  (오늘 밤 사례가 실제 발생 사례).

### 후속 조치 완료 (2026-09-12, 사용자 지시로 Claude가 직접 수정)
`gate_price_batch()`는 "같은 배치 안에서 기존 데이터와 겹치는 구간으로 기준선을 검증"하는
설계다(`price_integrity.py:233-278`) — 배치의 첫/끝 날짜가 기존 `price_history`와 겹쳐야
`overlap`이 생기고, 겹치지 않으면 `historical_batch_without_overlap`으로 거부된다. 그런데
`_save_stocks()`가 다루는 전형적 사례(하루치 결측일 재수집)는 정확히 "겹치는 기존 값이 없는
고립된 단일 날짜"이므로 그대로 연결할 수 없었다.

**`price_integrity.py`에 `gate_gap_fill_row(conn, code, day, row, source)` 신규 추가**
(`gate_price_batch`의 overlap 요구 없이, 인접 거래일과의 `outside_band` 경계 체크만 수행하는
gap-fill 전용 카운터파트). 규칙: (1) `invalid_ohlcv`/미래날짜 거부, (2) 해당 날짜에 이미 진짜
관측값(close>0 AND volume≠0)이 있으면 `not_a_gap_use_repair_workflow`로 거부(이건 gap-fill이
아니라 정식 repair 워크플로 대상), (3) close=0/volume=0 플레이스홀더는 "진짜 관측값 없음"으로
취급해 통과 허용, (4) 앞/뒤 인접 유효거래일과 `outside_band` 벗어나면 거부(`price_ingestion_quarantine`에
사유와 함께 기록), (5) 전부 통과 시 `app.price_basis_checked=1` 세팅 후 반환. 신규 단위테스트
5개 추가(`tests/test_price_integrity.py`), 전체 31개 테스트 통과.

**실제 수정된 호출부** (전부 임포트/트랜잭션 롤백 테스트로 검증 완료, 운영 DB에 부작용 없음):
- `collect_krx_history.py._save_stocks()` — 과거일자(`bas_dd != today_str`)에 한해
  `gate_gap_fill_row()` 통과 시에만 INSERT/UPDATE 진행.
- `collect_krx_investors.py`, `collectors/krx_investor_collector.py` — OHLCV=0 수급전용
  플레이스홀더 INSERT는 실제 가격을 주장하지 않으므로 `gate_gap_fill_row`가 아니라 직접
  `app.price_basis_checked=1`을 세팅(실 가격 검증 대상이 아님을 명시).
- `scripts/backfill_delisted_naver_prices.py` — `ON CONFLICT DO NOTHING`으로 비어있는
  (종목,날짜)에만 삽입되고 소스가 이미 검증된 naver 전체이력 스냅샷이므로 배치 단위로 플래그
  설정.
- `scripts/audit_and_repair_postgres_data.py`(`apply_repairs`), `scripts/ops/audit_and_repair_core_data_quality_20260624.py`(`apply_repairs`) — 둘 다 SQL WHERE절 자체에
  "현재 invalid_ohlcv인 행만, 검증된 소스(naver/stock_price_daily)로만" 조건이 내장돼 있어
  배치 시작 시 1회만 플래그 설정.

**의도적으로 손대지 않은 것**: `download_missing.py`/`force_download.py`/`insert_manual.py`/
`patch_data.py`/`patch_data_v2.py`/`patch_data_v3.py`는 2026-04-09/04-10 특정 사건에 하드코딩된
1회성 스크래치 도구(코드/날짜/가격이 소스에 박혀있어 재사용 불가) — 사실상 이미 실행 완료된
과거 기록이라 판단해 수정하지 않음. 재사용 필요 시엔 그때 코드를 고쳐 쓸 것이므로 방치.

**검증 완료 항목**(운영 DB 트랜잭션 롤백 테스트, 영구 반영 없음):
1. 정상 gap-fill(인접일과 부합하는 값) → `_save_stocks()` 경유로 실제 삽입 성공, 트리거 예외
   없음.
2. 비정상 값(인접가 대비 극단적 이탈) → 조용히 스킵(quarantine 기록), 크래시 없음.
3. 미래 날짜 → 거부.
4. 수급전용 0-OHLCV 플레이스홀더 삽입 → 성공.
5. 게이트를 거치지 않은 삽입(대조군) → 여전히 트리거가 정확히 차단함(가드 자체가 약화되지

## 4. 26개 선택전략 price_integrity 게이트 — 정책 결정 완료 (2026-09-12, 사용자 지시)

전부-아니면-전무(zero-tolerance) 유지 시 26개 전체가 영구히 `legacy`로 강등되는 상태였다
(v11조차 483건 중 1건=0.21% 오염으로 탈락 — 수백~수천 거래를 커버하는 다년 백테스트에서
드문 데이터공백(휴장일 인접 등) 없이 완주하는 건 사실상 불가능하므로, 전부-아니면-전무는
"게이트가 항상 꺼져 있는 것"과 다를 바 없었음). 사용자가 제시한 3가지 옵션(전부-아니면-전무
유지/임계값 도입/오염 보유기간만 개별 제외) 중 **임계값 도입**을 채택해 구현·적용했다 —
개별 보유기간 제외(3번안)는 P&L 재계산 로직까지 건드려야 해 훨씬 큰 공수가 필요했고, 이번
세션 안에서 안전하게 마칠 수 있는 범위를 벗어난다고 판단.

**구현**(`scripts/audit_selected_strategy_price_integrity.py`):
- `PRICE_JUMP_CONTAMINATION_THRESHOLD = 0.05`(5%) 신규 상수.
- 오염 판정을 **원시 이벤트 개수**가 아니라 **distinct (period,종목,보유시작,보유종료) 윈도우
  개수**로 재계산(`_distinct_windows()`) — 기존 코드는 한 윈도우 안에 여러 미해명 날짜가
  겹치면 그만큼 카운트가 누적돼 "오염비율 1000%" 같은 무의미한 수치가 나오고 있었음.
- **Codex 재검증 보정**: 최초 구현은 분자만 distinct였고 분모는 원시 보유윈도우 수였다.
  중복 거래가 있는 `deep_recovery`(602→578), `extreme_dd_volume`(1,078→1,045),
  `se_momentum`(2,916→2,878)에서 오염률이 희석됐다. 분모도 같은 distinct 키를 사용하도록
  수정했으며, 당시 통과/실패 결과 자체는 바뀌지 않는다.
- **survivorship 계열 findings(`missing_asof_security_master`, `held_through_listing_end` —
  전략이 검증된 상장기간 밖에서 진입/청산한 경우)는 임계값 적용 대상에서 제외하고 여전히
  전부-아니면-전무 유지** — 이건 데이터 품질 이슈가 아니라 전략 로직 자체의 결함(상장 전/후
  종목을 매매)이므로 완화하면 안 된다고 판단.
- 가격점프 계열(canonical_quality 기반, coverage_gap/unexplained_jump/mixed_basis 등)만
  5% 임계값 적용. `price_integrity`·`corporate_action_integrity`(이름은 오해 소지 있으나
  실제로는 가격점프 오염을 다시 검사하는 아티팩트) 둘 다 동일 임계값 사용, `survivorship_integrity`는
  무변경.
- 단위테스트 3개 추가(`tests/test_selected_strategy_price_integrity.py::ContaminationPolicyTest`).

**결과**(2026-09-12 11:26 재실행): **26개 중 19개 통과**(이전 0~1개). 실패 7개 —
`deep_recovery`(보정 전 9.47%, 보정 후 9.86%)/`extreme_dd_volume`(12.80%→13.21%)/
`golden_cross`(5.28%)/`low_base_breakout`(5.91%)는
가격점프 오염이 실제로 임계값을 넘어 정당하게 실패. `regime_adaptive`/`v_trend`/`v4`는
가격점프 비율은 낮지만(격리 반영 후 0.68~1.73%) survivorship findings가 있어 정당하게 실패 — 이 3개는
전략 로직의 as-of 유니버스/상장구간 처리를 점검할 필요가 있음(Codex 후속 조사 후보).

**후속 검토가 필요하면**: 5%는 임의 기준점이다("드문 공백은 감내하되 명백한 오염은 걸러낸다"는
취지로 보수적으로 잡음) — 실제 운영 데이터로 더 정교한 값을 찾거나, 궁극적으로는 3번안(개별
보유기간 제외 + P&L 재계산)으로 이관하는 것이 이상적이라는 점은 Codex도 참고할 것.
