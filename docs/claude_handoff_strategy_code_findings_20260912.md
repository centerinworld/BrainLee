## 요청과 역할

사용자의 요청은 주식전략 사이트의 백테스트·매수·매도에서 문제가 될 부분 및 수익률 개선 방향을 찾는 것이다. **Claude가 구현·영향 측정, Codex가 증거 검토·수정 검증을 담당한다.** 이 문서는 앞선 일반 연구 계획보다 먼저 처리할 구체적 코드 검토 결과다.

이번 Codex 작업은 코드 읽기와 합성 입력 검증이다. 운영 전략 코드·운영 DB·서비스 설정은 변경하지 않았고 실제 백테스트는 실행하지 않았다. 결함 재현과 과거 수익률 영향 측정은 다르다. “이 문제 때문에 547.36%가 얼마나 변한다”는 수치는 아직 알 수 없다.

실제 조사 소스: `/Volumes/Realtek_NVME/stock_dashboard/runtime`. 아래 파일·줄번호는 그 디렉터리 기준이며, 수정 후 이동할 수 있으므로 함수 이름도 함께 확인한다. 소스 루트와 운영본이 다르므로 양쪽 `CLAUDE.md`와 실행 경로를 확인하고 수정·배포 위치를 명시한다. 기존 미커밋 변경을 덮어쓰지 않는다.

## F01. 연간 실적의 미래 참조

근거: `backtest_strategies/sector.py:285` 부근, `run_backtest_sector` 섹터 OP YoY 계산.

`SELECT MAX(year) ... year<=거래일의 연도 AND is_annual=1`로 비교 연도를 선택한다. 이후 해당 연도 실적과 전년 실적을 조회할 때 실제 공시 시점 조건이 없다. “실제 공시된 가장 최근 연도”라는 주석과 다르다. 완성된 역사 DB에서 2024-01-05를 시뮬레이션하면 2024년 연간 실적을 선택할 수 있다. 이 값은 당시 알 수 없다.

- 재현: 연간 2023/2024 행을 가진 메모리 DB에서 의사결정일 2024-01-05 → 선택 연도 2024.
- 추가 확인: `pick_ta_bonus` 경로도 `sector.py:507` 부근에서 분기별 고정 날짜, 특히 Q4의 다음해 2/15를 사용한다. 실제 공시·정정 시점을 확인하지 않은 근사치이며 기본 None인 실험 기능이라 기본 전략과 영향 범위를 분리한다.
- Claude 조치: 실제 발표/정정 버전의 가용시점으로 종목별 최신 연간/분기 실적을 결정하고, 같은 회계기준의 비교연도를 연결한다. 근거가 없으면 미확인으로 처리하고 완전 PIT라고 표시하지 않는다. 섹터 전체의 MAX(year) 하나 때문에 늦게 공시한 회사가 빠지는 문제도 조사한다.
- Codex 수락 검증: 미래 연간 값·미래 정정본을 크게 바꿔도 과거 주문은 불변. 실제 공시 이전에는 신호 변화 없음. 늦게 공시하는 종목과 CFS/OFS 중복 fixture 포함.

## F02. 당일 종가를 시가 주문 전에 사용

근거: `merged_simulator.py:228`의 일별 루프 → 당일 `close`를 `marks`에 먼저 반영 → `:343`에서 `portfolio.buy(...mark_prices=marks)` 호출. `portfolio_engine.py:34`와 `:41`은 평가액으로 포지션 한도와 비례 티켓을 계산한다.

구성 주문이 D+1 시가 체결이면 그날 종가는 아직 모르는 값이다. 이 값으로 매수 가능 슬롯/수량을 정하면 미래 가격 참조가 된다. 동점 seed 안정성으로는 이 오류를 발견할 수 없다.

- 재현: 자본 1억원, A 종목 5천만원 보유, 현금 5천만원으로 고정. A 평가값만 10,000→12,000원으로 바꾸면 `dynamic_tickets` 한도가 10→11개가 된다. 실제 시가 주문 전 상태는 동일하다.
- Claude 조치: 의사결정·체결·종가평가 단계를 구분한다. 시가 전 확정된 전일 평가값 또는 계약상 관측 가능한 시가 평가를 사용하고, 종가 MTM은 주문 처리 후 수행한다. 일중 서로 다른 체결 시각의 주문은 날짜만으로 섞지 않는다.
- Codex 수락 검증: 당일 시가와 전일까지 데이터를 고정하고 당일 종가만 변경해도 당일 시가 주문 수량/수락 여부는 불변. 당일 종가 자산·MDD는 정상적으로 변해야 한다. dynamic_tickets와 ticket_pct 각각 검사.

## F03. 비례 티켓이 전략 예산 상한을 무효화

## F04. 피라미딩 현금 검산의 부호 오류

근거: `portfolio_engine.py:75`는 추가매수 원장을 `side='pyramid_add'`로 기록한다. `merged_simulator.py:580`의 등록 검산은 `side=='buy'`만 현금 차감하고 나머지는 모두 매도처럼 더한다.

- 재현: 초기 현금 100,000, 매수 10,000, 추가매수 5,000, 비용 0 → 실제 현금 85,000인데 검산 예상 현금은 95,000.
- 이는 조사 범위에서 **실제 매매 현금 계산의 오류가 아니라 증거 등록용 검산 오류**다. 올바른 추가매수 전략이 검증에서 탈락하거나 원장 상태가 부정확하게 표시될 수 있다. 어떤 승격 경로에서 이 artifact가 필수인지도 추적한다.
- Claude 조치: buy/pyramid_add는 지출, sell은 수입으로 명시하고 알 수 없는 side는 오류로 처리한다. 등록 절차의 부분 저장도 점검한다.
- Codex 수락 검증: 실제 CashPortfolio 원장을 입력해 일반매수→추가매수→부분/전체청산 지원 범위별 현금 검산. 수수료 포함 사례도 일치. 기존 피라미딩 기각 원장 중 이 이유의 기각이 있었는지 재분류.

## F05. 백테스트 거래 재생은 동일 전략의 전진 실행이 아님

근거: `routes/trend.py:3613` `_strategy_center_refresh_signal`은 과거부터 오늘까지 백테스트를 다시 실행한 뒤 **오늘 체결된 거래**를 추출한다. `_execute_strategy_center_paper`는 그 거래를 `_combo_current_price`의 최신 종가로 재체결한다. 원천 백테스트의 D+1 시가와 다르다.

가상계좌는 원천 계좌와 자본·현금 유보·진입일·보유가 다를 수 있다. 백테스트에서 현금 부족으로 탈락한 후보는 원천 거래 내역에 없으므로 가상계좌가 살 수 있어도 기회를 받지 못한다. 반대로 원천 보유분의 매도만 받아서는 가상계좌의 실제 진입가/고점/손절을 정확히 관리하지 못한다.

또한 `_strategy_center_paper_cache`는 전략+날짜만 키로 사용한다. 동일 날짜의 데이터 수정·설정 변화가 발생해도 캐시 무효화 근거가 없다.

- Claude 조치: 체결 내역과 주문 후보 신호를 분리한다. 신호 생성은 공통으로, 실행과 청산 판단은 해당 계좌의 실제 보유 상태 및 명시된 시각으로 수행한다. 순위에서 고른 정확한 parameter/run spec을 어댑터 기본값 대신 연결한다. 캐시 키에 코드/입력/설정 지문을 넣는다.
- Codex 수락 검증: 같은 시작 계좌·같은 입력을 하루씩 공급했을 때 백테스트와 paper의 주문·수량·체결·청산·비용이 일치. 다른 진입가/매수 거부 이력을 주면 해당 계좌에 맞는 손절이 작동. 같은 날짜 재호출은 중복 체결 없음.
- 조사에서 종료청산 마커를 파서가 제외하는 코드는 확인했다. “종료청산이 무조건 매일 매도로 실행된다”는 결함으로 보고하지 않는다.

## F09. 병합 포지션의 매도 소유권 정책

근거: `merged_simulator.py:244`는 동일 종목의 매도 주문 중 우선순위 주문을 골라 공유 포지션 전량을 판다. 저장된 `capital_owner`는 원가 배분 해제에 쓰이며, 매도 신호 발생 전략이 포지션 소유자/기여자와 일치하는지는 확인하지 않는다.

이는 반드시 버그라고 단정할 수 없다. “어느 전략이든 매도하면 공통 청산”이라는 의도적 정책일 수 있다. 다만 A가 매수한 포지션을 실제 병합계좌에서는 매수하지 못한 B의 매도 신호가 정리하면, 개별 전략을 결합한다는 사용자의 기대와 달라질 수 있다.

- Claude 조치: 정책을 명시하고 ① 현재 any-sell ② 소유 전략 매도 ③ 전략별 가상 lot/부분 청산을 같은 자본 조건으로 비교한다. 위 모든 정책에서 공통 위험 청산의 우선순위는 별도 정의한다.
- Codex 수락 검증: A 매수 성공·B 매수 거부 후 B 매도, 중복 진입 기여자, A/B 충돌 사례의 결과가 정책과 일치. 정책을 바꾸면 이전 헤드라인과 섞지 않고 새 실행으로 기록한다.
